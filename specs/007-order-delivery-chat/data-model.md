# Data Model: Order Delivery Chat

## Overview

Chat messages are scoped to a `Pedido`. Each `Pedido` has exactly one implicit chat thread composed of all `Mensaje` records with the matching `pedidoId`. Only the order's client (`cliente`) and the gig's seller (`vendedor`) can read or write messages in that thread.

## Entities

### `Mensaje` (extended)

A single chat message inside an order thread.

| Attribute | Type | Required | Description |
|-----------|------|----------|-------------|
| `id` | string | yes | Unique identifier generated by the repository. |
| `pedidoId` | string | yes | The order this message belongs to. |
| `senderId` | string | yes | ID of the authenticated user who wrote the message. Derived from the JWT token, not the request body. |
| `senderType` | enum | yes | `CLIENTE` if `senderId === Pedido.cliente`, `FREELANCER` if `senderId === Gig.vendedor`. |
| `content` | string | yes | Message body. Trimmed before storage. Maximum 2,000 characters. |
| `status` | enum | yes | `ENVIADO` after successful persistence; `PENDIENTE`/`FALLIDO` may be used client-side for optimistic UI. |
| `createdAt` | ISO timestamp | yes | UTC timestamp when the message was persisted. |

**Validation rules**:
- `content` must be non-empty after trimming.
- `content` must not exceed 2,000 characters.
- `senderId` must match either `Pedido.cliente` or the related `Gig.vendedor`.
- `pedidoId` must reference an existing order.
- New messages can only be created when `Pedido.estado` is not `COMPLETADO` or `CANCELADO`.

### `Pedido` (existing, used by chat)

The order aggregate. The chat thread is implicitly defined by all messages whose `pedidoId` equals `Pedido.id`.

| Attribute | Type | Description |
|-----------|------|-------------|
| `id` | string | Order identifier. |
| `cliente` | string | ID of the client who placed the order. |
| `gig` | string | ID of the gig purchased. Used to resolve the freelancer via `Gig.vendedor`. |
| `estado` | enum | Current order status (`PENDIENTE`, `CONFIRMADO`, `EN_REVISION`, `ENTREGADO`, `COMPLETADO`, `CANCELADO`). |
| `mensajes` | array | Existing array on the domain object; may continue to hold message IDs or be replaced by repository queries. |

### `Gig` (existing, used for authorization)

| Attribute | Type | Description |
|-----------|------|-------------|
| `id` | string | Gig identifier. |
| `vendedor` | string | ID of the freelancer selling the gig. |

## Relationships

```text
Pedido 1 --* Mensaje
Pedido * --1 Gig (via gig ID)
Pedido * --1 Usuario (cliente)
Gig * --1 Usuario (vendedor / freelancer)
```

A `Mensaje` belongs to exactly one `Pedido`. A `Pedido` has one related `Gig`, and the chat authorization compares the authenticated user against `Pedido.cliente` and `Gig.vendedor`.

## State Transitions

### Message status

```text
PENDIENTE (client-side optimistic) → ENVIADO (server confirmed)
                                    → FALLIDO (send error, user can retry)
```

### Order status impact on chat

| Order status | Read history | Send new messages |
|--------------|--------------|-------------------|
| `PENDIENTE` | yes | yes |
| `CONFIRMADO` | yes | yes |
| `EN_REVISION` | yes | yes |
| `ENTREGADO` | yes | yes |
| `COMPLETADO` | yes | no (read-only) |
| `CANCELADO` | yes | no (read-only) |

## Notes

- The existing in-memory store does not support relations or foreign keys; authorization and existence checks are performed in the service layer.
- Timestamps are stored as ISO strings (`new Date().toISOString()`) to match existing domain patterns.
- Sender identity is never accepted from the client request body; it is always derived from `req.user.id` provided by the JWT middleware.
